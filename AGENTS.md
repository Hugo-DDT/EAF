# EAF Coding Agent Guidelines

## Current Purpose and Scope

EAF is a personal open-source Agent platform project for a job-seeking resume and interview discussion of its features, technical strengths, and design tradeoffs. Follow ordinary personal-project standards: useful implementation, basic runnability, understandable design, and honest claims. No demonstrations are currently requested; do not require demo preparation, browser walkthroughs, videos, or live presentations for completion.

The overall product goal is to improve employees', project teams', departments', and enterprises' work efficiency through Agent integration, knowledge and experience use, task execution, workflow and collaboration, business-system integration, and feedback-driven improvement. Shared resources are one part of this goal. Customer follow-up is an existing sample business, not the platform's full scope. See [project goals](docs/project-goals.md).

## Reading and Working Method

- Start with README, the current task, and relevant implementation/callers. Read architecture, module, API, data, state, or event contracts only when the change touches that boundary; do not load every document for every task.
- Inspect the actual workspace and preserve unrelated user changes. Do not confuse plans with implemented behavior.
- For implementation tasks, deliver a concrete behavior that addresses a work problem or improves an existing mechanism. Reuse existing modules and libraries; avoid speculative interfaces, extra framework layers, and empty modules. Documentation tasks need only the requested documentation change.
- Update only contracts affected by changes to interfaces, data, states, or release behavior. Internal changes do not require a contract-freeze step.
- A short delivery note with changes, actual checks, and limitations is sufficient. PG/G identifiers, separate evidence directories, acceptance matrices, and learning reports are optional.
- Proceed with authorized reversible implementation and documentation. Ask only for a necessary scope/security decision, destructive action, or missing external authorization; do not reconfirm already-covered work.

## Essential Boundaries

- Keep the modular monolith. Modules own their data and collaborate through public APIs/ports/events, without cross-domain Mappers or table writes.
- Keep all model calls inside model. Existing generation/Embedding paths retain their integrations. The Jev non-Chat adapter uses the model-owned typed Gateway and RestClient; no entire-stack upgrade or separate sidecar is required.
- Business tools go through Execution. Policy denials take precedence over model suggestions and human approval. Keep current permission checks, approval bindings, execution budgets, and idempotent write verification.
- Knowledge, Memory, and unpublished Candidate stay separate. Evaluation data must not become ordinary learning feedback or leak answers into candidate generation.
- Keep credentials out of source, prompts, logs, events, command arguments, and snapshots. Provider settings and keys come only from environment variables or the ignored root .env.
- Deterministic remains the default. Real Provider requests use synthetic data and explicit activation, a finite spend cap, and valid authorization covering the Provider/data/run. Continue within existing authorization without asking repeatedly.
- Unknown external-write results must be queried with the original operation identity before resubmission. Do not claim automatic recovery or side-effect guarantees that were not verified.

## Proportionate Verification

Use the smallest effective check for the change. Documents need content/link checks, not Maven or database execution. Ordinary Java logic needs relevant compilation and an existing or small meaningful test when warranted. For security, isolation, budgets, external writes, and learning publication, check the key failure cases directly affected by the change; do not require a complete negative-case matrix.

Use relevant modules/tests by default. Consider .\mvnw.cmd -B -ntp verify when dependency, migration, or core-flow changes have broad impact, local checks are insufficient, or a version release warrants it; a stage number alone is not a full-build gate. Do not introduce coverage quotas, fixed test counts, or repeated checks without a concrete need. Keep existing tests; do not disable failing tests, remove useful assertions, rewrite scoring answers, or fabricate passing results.

Model experiments are optional unless needed for the specific change or claim. Use a few representative synthetic cases as needed, with no fixed minimum sample count or rounds. Large evaluations, calibration, ablations, load tests, and full crash-injection matrices are not default requirements. Existing evaluation APIs retain their implemented rules. Engineering completion and unverified real-model effects may be reported separately.

Record actual commands/results and checks not run. Historical results are historical; a missing environment is not a passing check.

## Learning and Delivery

Explain a new mechanism's role and key tradeoff briefly when useful, and point to actual entry points after implementation. Do not require a quiz, experiment, or learning report for every task. The learning module is a business capability, distinct from the developer's learning.

For learning publication changes, retain source/scope/version bindings, revision invalidation, isolated evaluation, idempotent publication through the target API, and withdrawal. Do not rebuild these mechanisms for unrelated tasks.

Use Chinese comments near new or modified non-obvious business rules, security checks, recovery logic, public API semantics, and migrations. Avoid comments that merely translate syntax or trivial accessors; do not conduct repository-wide comment rewrites as an incidental gate.

Do not overwrite unrelated changes, invent commits/results, silently call paid models, deploy to enterprise systems, or send external messages. When adding a dependency, verify the actual version against official documentation and explain why existing capabilities are insufficient.
